Le CLAUDE.md du créateur de Claude Code

Claude Code·Workflow·Niveau intermédiaire

Le fichier CLAUDE.md est la mémoire permanente de Claude Code dans ton projet. C'est lui qui indique à l'IA comment travailler avec ton codebase, quelles conventions respecter, quels outils utiliser. Boris Cherny, le créateur de Claude Code chez Anthropic, a partagé le sien — et c'est une mine d'informations.

C'est quoi un CLAUDE.md ?

Quand tu lances Claude Code dans un dossier, il lit automatiquement le CLAUDE.md à la racine du projet. Ce fichier contient tes instructions persistantes : stack tech, patterns de code préférés, commandes importantes, règles de nommage, contexte métier.

Sans lui, Claude repart de zéro à chaque session. Avec lui, il connaît ton projet comme un dev senior qui travaille dessus depuis des mois.

Les 4 règles de son fichier

L'essentiel de son CLAUDE.md tient en quatre règles. La troisième est celle qui change tout sur la durée.

Règle 1 — Le plan d'abord

Avant d'écrire la moindre ligne de code, Claude écrit le plan. Et si l'exécution dérape en cours de route, il ne bricole pas : il s'arrête et il refait le plan. Un plan écrit est vérifiable, un plan implicite ne l'est pas.

Règle 2 — Déléguer aux sous-agents

Le travail long ou exploratoire (fouiller un gros codebase, tester dix pistes) part dans un sous-agent. Le contexte principal reste propre et concentré sur la décision, pas sur le bruit de la recherche.

Règle 3 — La boucle d'auto-amélioration

C'est la règle qui compose dans le temps. Chaque erreur commise devient une règle écrite dans le fichier. La session suivante la lit et ne refait pas l'erreur. Au bout de quelques semaines, le taux d'erreur s'effondre — parce que ton fichier a mémorisé tout ce qui a mal tourné.

Règle 4 — Prouver que ça marche

Aucune tâche n'est déclarée terminée sans que les tests aient été lancés. Pas « ça devrait marcher » : la sortie des tests, ou rien.

Piège vu en production

La règle 3 ne marche que si tu écris la règle au moment de l'erreur, pas « plus tard ». Une erreur non écrite est une erreur qui reviendra à la session suivante, parce que Claude repart d'un contexte vide à chaque fois.

Le fichier complet, à copier tel quel

Colle ça dans un fichier CLAUDE.md à la racine de ton projet, puis adapte la section Stack et Commandes à ton cas.

# CLAUDE.md ## Stack technique - Framework : Next.js 14 App Router - Style : Tailwind CSS - BDD : PostgreSQL via Prisma ## Commandes importantes - `npm run dev` — lancer en local - `npm run test` — tests unitaires - `npm run build` — vérifier avant deploy ## Règle 1 — Le plan d'abord - Écrire le plan AVANT de coder. Pas de code sans plan écrit. - Si l'exécution dérape : s'arrêter, refaire le plan, repartir. ## Règle 2 — Déléguer aux sous-agents - Recherche large, exploration de codebase, pistes multiples → sous-agent. - Le contexte principal reste réservé à la décision et au code final. ## Règle 3 — Boucle d'auto-amélioration - Toute erreur commise devient une règle écrite ici, immédiatement. - Relire cette section au début de chaque session. ## Règle 4 — Prouver que ça marche - Jamais de tâche "terminée" sans avoir lancé les tests. - Coller la sortie réelle des tests, pas une supposition. ## Conventions - Composants en PascalCase - Hooks préfixés par `use` - Pas de `any` TypeScript - Toujours lire un fichier avant de le modifier - Demander confirmation avant de supprimer du code

Où placer le fichier

  • CLAUDE.md à la racine = instructions globales du projet
  • src/CLAUDE.md = instructions spécifiques au code source
  • ~/.claude/CLAUDE.md = règles globales pour tous tes projets
⚡ Conseil pro

Commence par un CLAUDE.md minimal, puis enrichis-le au fil des sessions. Chaque fois que Claude fait une erreur de convention, ajoute une règle pour que ça n'arrive plus jamais.
